# Teacher Collaboration Lab — Project Rules

**Version:** 1.1  
**Status:** Initial governance rules; operational policies drafted and pending implementation verification  
**Scope:** Project coordination, public documentation, educational content, community operations

## 1. Purpose and authority

These rules implement the [Project Charter](PROJECT-CHARTER.md). They guide project setup, content production, community preparation, and pilot delivery. They do not replace applicable law, school policies, Slack terms, or a separately approved participant privacy notice.

The project owner approves changes to public visibility, membership policy, access permissions, and publication of sensitive or participant-related information.

## 2. Language and accessibility

- Communicate with the project owner and participants in Georgian by default.
- Maintain technical repository documentation in English unless otherwise agreed.
- Write teacher-facing materials in clear Georgian, explaining technical terms.
- Provide accessible, beginner-friendly instructions with concrete examples; avoid assuming prior Slack experience.
- Design learning activities for differing digital skill levels and available devices.

## 3. Step-by-step project workflow

For each milestone:
1. State the objective and expected deliverable.
2. Check existing files, connected resources, permissions, and dependencies.
3. Propose the smallest practical next action.
4. Obtain approval when needed, then perform the action.
5. Verify the result using direct evidence.
6. Record completion, outstanding issues, and the next step.

Use the statuses **Planned**, **In progress**, **Verified**, **Blocked**, and **Not applicable**. Never claim a task or integration is complete without verification.

## 5. GitHub publishing and change control

- This repository is **public**. Publish only material intended for public access.
- Never commit credentials, tokens, private invitation links, application responses, personal contact lists, private Slack messages, student information, moderation evidence, identifiable incident records, or confidential school documents.
- Use descriptive filenames and focused commit messages.
- Update the README and project status when milestones change.
- Review proposed material for accuracy, privacy, copyright and accessibility before publication.
- Confirm before destructive changes, major restructuring, licensing decisions or expansion of public access.
- No reuse license has yet been selected; obtain explicit approval before adding one.

## 6. Privacy and participant data

- Collect only data needed for application review and onboarding.
- Provide an understandable privacy notice **before** collecting applications, specifying purpose, access, retention, deletion/contact process, and any third-party services used.
- Restrict administrative records to authorized organizers; do not publish identifiable applications, moderation records or assessment results.
- Do not upload student data or identifiable school records to Slack, GitHub, ChatGPT or public resources.
- Obtain appropriate permission before publishing identifiable photographs, quotes, testimonials or participant-created work.
- Define a retention and deletion schedule before opening registration.
- Review applicable Georgian data-protection requirements and platform policies before launch.

## 7. Membership and onboarding

The community is open to applications from teachers across Georgia; joining is not automatic.

1. Applicant submits a short form.
2. An authorized organizer reviews the application using consistent, relevant criteria.
3. Approved applicants receive an invitation.
4. Participants acknowledge the [Community Guidelines](COMMUNITY-GUIDELINES.md) and complete onboarding.

Do not publish applicant lists or disclose private reasons for admission decisions. Define the application review criteria and an appropriate contact process before recruitment.

## 8. Slack community standards

Participant-facing conduct expectations are defined in the [Community Guidelines](COMMUNITY-GUIDELINES.md).

Core standards include:

- Use topic-specific channels; reply in threads to keep discussions organized.
- Communicate respectfully. Harassment, discrimination, threats, spam and unsolicited advertising are not permitted.
- Share educational resources with attribution and respect copyright.
- Do not post private student, parent, colleague or school information.
- Avoid unnecessary mass mentions and out-of-hours expectations; participation is asynchronous unless an event is explicitly scheduled.
- Report concerns privately to designated moderators.
- Moderators should document significant decisions in restricted records, not public channels.
- Confirm platform eligibility and age requirements; the initial community is intended for adult teachers.

## 9. Moderation and administration

Teacher Collaboration Lab uses a **balanced moderation model**. The authoritative moderation workflow is defined in the [Moderation Policy](MODERATION-POLICY.md).

Before inviting participants:

- designate at least one workspace administrator and a moderation backup;
- define responsibilities for invitations, channel management, incident handling, data access and participant removal;
- create a restricted moderation log outside the public GitHub repository;
- test the escalation workflow using sample scenarios;
- verify that administrators understand the sequence **Protect → Clarify → Correct → Document → Escalate**.

Moderation should be proportionate and consistent. Minor first-time mistakes should normally be handled through guidance and correction; serious privacy, security, safety or harassment incidents may require immediate escalation without prior warning.

## 10. Educational content and pilot quality

The initial pilot is a four-week Slack training program for a target cohort of approximately 10–20 teachers.

Each module should include:
- Clear learning outcomes and prerequisites.
- Short demonstrations and teacher-relevant examples.
- A practical task with observable completion criteria.
- Beginner support and optional extension activities.
- Feedback and reflection.

Evaluate not just tool usage but whether communication and collaboration become clearer and more effective. Set measurable targets before recruitment and report aggregate findings without identifying participants.

## 11. Security and integration validation

- Follow least-privilege access and protect administrator accounts with strong authentication.
- Verify permissions and actual read/write capabilities for each connected service.
- Keep administrative, educational and public materials separated.
- Do not treat a proposed integration as working until a real test succeeds.
- Review invitations, public sharing links and third-party app permissions periodically.

## 12. Approval gates

Explicit project-owner approval is required before:
- Publishing or expanding access to private material.
- Opening registration or sending participant invitations.
- Adding new integrations with sensitive permissions.
- Changing the admission model or public project scope.
- Deleting important records or performing irreversible operations.
- Selecting a repository license or publishing participant-identifiable content.

Routine edits to approved public documentation may proceed within the agreed project scope, followed by verification.

## 13. Review and maintenance

Review these rules after the initial pilot and whenever project scope, platform capabilities, or privacy requirements change. Record substantive changes in version history or commit messages.

The Community Guidelines and Moderation Policy should also be reviewed after the first pilot, after serious moderation incidents, and before substantial community expansion.
